# SLA’vik в языковой модели: воспроизводимый пилот

**Дата:** 2026-11-10<br>
**Объект:** компактный decoder-only Transformer с посимвольным предсказанием следующего символа<br>
**Сравнение:** ReLU, GELU, SLA’vik‑A и SLA’vik‑R2<br>
**Среда:** CPU, без CUDA<br>
**Статус:** завершённый маломасштабный эксперимент, а не доказательство качества большой LLM

Этот документ дополняет исследования SLA’vik и не перезаписывает `SLAvik_полный_отчёт.md`.

## 1. Короткий ответ

SLA’vik можно встроить в Transformer и обучить языковую модель обычным backpropagation. В проведённом пилоте получены четыре основных результата.

1. **При равных 400 шагах SLA’vik‑A немного точнее ReLU.** Средний validation loss составил 2,79006 против 2,79877; среднее уменьшение — 0,311 %. Разница отрицательна во всех пяти парных сидах. Парный t‑тест: p = 0,00579.
2. **SLA’vik‑R2 тоже немного лучше ReLU при равных шагах.** Loss 2,79468, уменьшение на 0,146 %, p = 0,02986. Это слабее, чем у SLA’vik‑A.
3. **В eager-режиме это преимущество не окупает затраты времени.** SLA’vik‑A обучался 29,72 с против 18,26 с у ReLU, то есть на 62,7 % дольше. ReLU с 660 шагами за примерно те же 30 секунд достиг loss 2,65925 — значительно лучше обеих SLA’vik‑версий с 400 шагами.
4. **После `torch.compile` результат по скорости меняется.** На пяти парных сидах warm-обучение SLA’vik‑A заняло 19,59 с против 20,56 с у compiled ReLU: на 4,71 % меньше, при сохранении небольшого преимущества по loss. Но холодная JIT-компиляция дорогая, а compiled SLA’vik‑A всё ещё немного медленнее eager ReLU400.

**Итог:** SLA’vik‑A показал небольшую воспроизводимую эффективность на шаг и перспективу после kernel fusion, но не доказал универсального превосходства над ReLU. Для короткого eager-обучения на данном CPU равновременный ReLU оказался лучше.

Качество генерации пока слабое: модель воспроизводит фрагменты русской морфологии и Markdown, но часто создаёт несуществующие слова и бессвязный текст. Это ожидаемо для посимвольной модели на 84–86 тысяч параметров и корпуса в 176 599 символов.

## 2. Что именно проверялось

Проверялся **только перенос активации SLA’vik в FFN языкового Transformer**.

Не проверялись:

- полная TLN с формальным верификатором;
- внешняя память, поиск по документам и интернету;
- локальное обучение вместо AdamW;
- модульные PairBlock и `grow_by_audit`;
- большие модели и современные LLM-бенчмарки.

Поэтому результат отвечает на вопрос «работает ли SLA’vik как активация внутри языкового Transformer», но не доказывает преимущества всей гибридной TLN.

### 2.1. Архитектура

Модель имеет стандартную pre-norm decoder-only структуру:

```text
символы
  → token embedding + learned positional embedding
  → 2 × блок:
       x = x + CausalSelfAttention(LN(x))
       x = x + FFN(LN(x))
  → LayerNorm
  → tied token embedding как выходная проекция
  → вероятности следующего символа
```

Для одного блока:

\[
x' = x + \operatorname{Attn}(\operatorname{LN}_1(x)),
\]

\[
x'' = x' + W_2 f(W_1\operatorname{LN}_2(x')+b_1)+b_2.
\]

Меняется только функция \(f\): ReLU, GELU, SLA’vik‑A или SLA’vik‑R2. Attention, embeddings, LayerNorm, инициализация общих весов, оптимизатор и генератор батчей одинаковы.

### 2.2. SLA’vik‑A

Для каждого элемента входного вектора \(a\):

\[
b=\alpha a+\beta,\qquad s=a+b,\qquad p=ab,
\]

\[
f_A(a)=\max(s,0)
+\lambda\frac{\min(s,0)}{1+|s|}
+\kappa\frac{p}{1+|p|},
\]

где

\[
\kappa=\operatorname{softplus}(\kappa_{raw}),\qquad
\lambda=\operatorname{sigmoid}(\lambda_{raw}).
\]

Обучаются \(\kappa_{raw},\lambda_{raw},\alpha,\beta\) отдельно для каждого канала FFN.

### 2.3. SLA’vik‑R2

\[
f_{R2}(a)=\operatorname{ReLU}(a)+g\left[
\kappa\frac{ab}{1+|ab|}
+\lambda\frac{\min(a,0)}{1+|a|}
\right],
\]

\[
g=\operatorname{sigmoid}(g_{raw}).
\]

R2 сохраняет основную ветвь ReLU и добавляет обучаемую нелинейную поправку.

### 2.4. Цель обучения

Для последовательности из \(T\) символов:

\[
\mathcal{L}=-\frac{1}{T}\sum_{t=1}^{T}
\log p_\theta(x_{t+1}\mid x_{\le t}).
\]

Дополнительно вычисляются:

\[
\operatorname{PPL}=\exp(\mathcal{L}),
\]

\[
\operatorname{Accuracy}=\frac{1}{T}\sum_t
\mathbb{I}\left[\arg\max_c p_\theta(c\mid x_{\le t})=x_{t+1}\right].
\]

Меньшие loss и PPL лучше; accuracy выше лучше. В таблицах PPL — среднее PPL отдельных запусков, а не экспонента среднего loss.

## 4. Протокол сравнения

### 4.1. Парные сиды

ReLU, SLA’vik‑A и SLA’vik‑R2 запускались на сидах 0–4. GELU — на сидах 0–2.

Для каждого сида:

- одинаково инициализируются общие веса;
- одинаковый генератор создаёт train-батчи;
- промежуточная оценка идёт каждые 50 шагов на четырёх батчах;
- генерация начинается с одинакового RNG-состояния и промпта.

### 4.2. Единая финальная оценка

Финальная оценка выполняется на **одних и тех же 32 validation-батчах** для всех активаций, сидов, eager/compiled и 400/660 шагов:

\[
32\ \text{батчей}\times32\ \text{последовательности}\times64
=65\,536\ \text{validation-токенов}.
\]

Это важно: финальная метрика не зависит от периодичности промежуточной оценки. Время evaluation не включено в `train_seconds`; оно сохраняется отдельно в `total_seconds_with_eval`.

### 4.3. Статистика

Для каждого сида вычисляется парная разница:

\[
d_i=\mathcal{L}_{SLA,i}-\mathcal{L}_{ReLU,i}.
\]

Отрицательное \(d_i\) означает победу SLA’vik. Используются двусторонний парный t‑тест и дополнительно точный знаковый тест. При пяти сидах даже результат 5/5 даёт знаковый тест p = 0,0625, поэтому согласованность направления сама по себе не достигает порога 0,05.

Число запусков мало; тесты следует считать исследовательскими, а не окончательным статистическим доказательством для всех задач.

## 6. Равное wall-clock время в eager-режиме

SLA’vik требует больше elementwise-операций: произведения, модули, деления, sigmoid/softplus и дополнительные ветви. В eager PyTorch это создаёт больше kernel launches и промежуточных тензоров.

Среднее время 400 шагов:

- ReLU: 18,26 с;
- SLA’vik‑A: 29,72 с, коэффициент 1,627;
- SLA’vik‑R2: 29,59 с, коэффициент 1,620.

Для практического равновременного baseline ReLU был обучен 660 шагов. Cosine-расписание в этом запуске рассчитано на 660 шагов, то есть это отдельный корректный сценарий обучения, а не просто продолжение ReLU400 с неизменным LR.

| Модель | Шаги | Train time, с | Val loss | Mean PPL | Token accuracy |
|---|---:|---:|---:|---:|---:|
| SLA’vik‑A | 400 | 29,72 | 2,79006 | 16,282 | 25,910 % |
| SLA’vik‑R2 | 400 | 29,59 | 2,79468 | 16,358 | 25,926 % |
| ReLU | 660 | 30,04 | **2,65925** | **14,286** | **27,986 %** |


По парным различиям на одних и тех же финальных validation-батчах:

- A400 − ReLU660: +0,130812 loss, p = 5,79×10⁻⁷;
- R2 400 − ReLU660: +0,135437 loss, p = 3,26×10⁻⁷.

Таким образом, **при равном eager-времени ReLU660 лучше A400 по loss на 4,69 %**. Небольшая эффективность SLA’vik на один шаг не превращается в эффективность на секунду без оптимизации исполнения.

## 7. Проверка `torch.compile`

### 7.1. Warm-результат

Compiled-серия содержит пять парных сидов ReLU и SLA’vik‑A. Warm-время — это шаги 1–399 без первого шага, на котором происходит JIT-компиляция.

| Метрика | ReLU compiled | SLA’vik‑A compiled | Парная разница A−ReLU |
|---|---:|---:|---:|
| Val loss | 2,79888 | 2,79013 | −0,008751 |
| Mean PPL | 16,426 | 16,284 | −0,143 |
| Token accuracy | 25,769 % | 25,881 % | +0,112 п.п. |
| Warm train, 399 шагов, с | 20,56 ± 0,15 | 19,59 ± 0,68 | −0,969 |
| Warm tokens/s | 39 745 | 41 748 | +5,04 % |


Внутри compiled-протокола:

- разница loss: p = 0,00749;
- 95 % CI Δloss: от −0,013609 до −0,003892;
- warm-время: SLA’vik‑A быстрее на 4,71 %, p = 0,02419;
- 95 % CI разницы времени: от −1,731 до −0,207 с;
- по скорости A быстрее в 4/5 сидов, но не во всех.

Это **многообещающий результат fusion**, но не универсальный закон. На данном оборудовании compiled ReLU warm медленнее собственного eager ReLU, а compiled SLA’vik‑A warm на 7,27 % медленнее eager ReLU400. Поэтому нельзя выбирать только удобный baseline и заявлять общую победу по wall-clock времени.

### 7.2. Холодный JIT

Холодный старт проверялся в отдельных процессах с независимыми новыми кэшами Inductor, по одному запуску:

| Модель | Первый шаг/JIT, с | Все 400 шагов, включая JIT, с |
|---|---:|---:|
| ReLU | 31,75 | 56,39 |
| SLA’vik‑A | 33,15 | 52,49 |

Это одиночные замеры, а не статистическая серия. Они показывают главное: для одного короткого 400-шагового обучения компиляция может не окупиться. Warm-преимущество актуально для повторных запусков в одном процессе, длинного обучения или заранее подготовленного кэша.

### 9.5. Ключевой код активации

```python
class SlavikA(torch.nn.Module):
    def __init__(self, width: int):
        super().__init__()
        self.kappa_raw = torch.nn.Parameter(torch.full((width,), 0.5413))
        self.lambda_raw = torch.nn.Parameter(torch.full((width,), -1.7346))
        self.alpha = torch.nn.Parameter(torch.full((width,), 0.37))
        self.beta = torch.nn.Parameter(torch.full((width,), 0.11))

    def forward(self, a):
        kappa = F.softplus(self.kappa_raw)
        lam = torch.sigmoid(self.lambda_raw)
        b = self.alpha * a + self.beta
        s = a + b
        p = a * b
        return (torch.clamp(s, min=0)
                + lam * torch.clamp(s, max=0) / (1 + s.abs())
                + kappa * p / (1 + p.abs()))
```

Полный файл `slavik_llm.py` содержит Transformer, обучение, оценку, генерацию и сохранение JSON. SHA256 версии, использованной для итогового отчёта:


### 9.6. Проверка парной статистики

```python
import json
import numpy as np
from scipy.stats import ttest_rel, binomtest

rows = json.load(open("experiments/llm_final.json", encoding="utf-8"))
by = {(r["act"], r["seed"]): r for r in rows}
seeds = range(5)

relu = np.array([by[("relu", s)]["final"]["val_loss"] for s in seeds])
a = np.array([by[("slavik_a", s)]["final"]["val_loss"] for s in seeds])
d = a - relu

print("Разницы:", d)
print("Среднее:", d.mean())
print("Парный t-тест:", ttest_rel(a, relu))
print("Знаковый тест:", binomtest(int((d < 0).sum()), len(d), 0.5))
```

## 10. Ограничения

1. **Это Tiny LM, а не большая LLM.** Нельзя переносить вывод на миллиарды параметров без масштабных экспериментов.
2. **Посимвольная токенизация.** Она удобна для небольшого теста, но хуже отражает качество современных subword/byte-level систем.
3. **Узкий самодокументируемый корпус.** Технические отчёты проекта не заменяют разнообразный открытый текстовый набор.
4. **Validation не является независимой предметной областью.** Это продолжение того же корпуса.
5. **Мало сидов.** Основные серии имеют n = 5, GELU n = 3; холодный JIT измерен однократно.
6. **Нет внешних benchmark-задач.** Не проверялись reasoning, retrieval, factuality, инструкции и длинный контекст.
7. **Скорость зависит от среды.** Выводы eager/compile относятся к указанным CPU и PyTorch.
8. **ReLU660 имеет другое по длине cosine-расписание.** Это корректный практический равновременный сценарий, но не изолированное изменение только числа шагов.
9. **Проверена только активация.** Результат не доказывает эффективность локального обучения, TLN-памяти или модульного аудита.
10. **Нет доказанной победы по генерации.** Текстовые образцы остаются слабыми у всех вариантов.

## 11. Практический вывод и следующие эксперименты

### Что уже можно утверждать

- SLA’vik‑A и R2 обучаются внутри decoder-only Transformer без специального оптимизатора.
- В данном пилоте SLA’vik‑A даёт небольшое, согласованное снижение validation loss при равном числе шагов.
- Eager-реализация SLA’vik слишком дорога, чтобы победить ReLU на равном времени.
- `torch.compile` устраняет большую часть штрафа SLA’vik и в warm-режиме даёт небольшое преимущество над compiled ReLU.
- Для короткого одиночного запуска JIT-стоимость существенна.

### Что нельзя утверждать

- «SLA’vik полностью превзошёл ReLU»;
- «SLA’vik всегда быстрее»;
- «получена полноценная LLM»;
- «качество генерации лучше»;
- «результат доказан на больших моделях и открытых данных».

### Приоритет следующих проверок

1. **Fused kernel.** Реализовать SLA’vik одним Triton/C++/CUDA-ядром и сравнить с ReLU без JIT-неоднородности.
2. **Честный длительный бюджет.** Обучение не менее нескольких тысяч шагов, отдельные train/validation/test и заранее зафиксированный протокол.
3. **Открытый корпус и subword-токенизация.** Проверить, сохраняется ли эффект вне документов проекта.
4. **Масштабирование.** Несколько размеров модели и `d_ff`, замеры памяти, пропускной способности и стабильности.
5. **Полная TLN.** Отдельно проверить поиск по документам, верификатор и реализатор речи, не смешивая их вклад с активацией.

**Окончательная оценка пилота:** SLA’vik‑A заслуживает дальнейшей оптимизации и проверки в языковых моделях, но текущий рациональный выбор зависит от режима исполнения. Для короткого eager-обучения на этом CPU лидирует равновременный ReLU; для warm compiled-сценария SLA’vik‑A показывает небольшое преимущество, которое ещё нужно подтвердить на масштабе.
